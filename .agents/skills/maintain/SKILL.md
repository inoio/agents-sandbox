# Maintain

Keep the GitHub project healthy. `maintain` surveys the repo, proposes a single
batch plan of actions across its areas, and executes only the approved rows.

`maintain` supersedes the `triage` skill: it carries the same issue state machine
and adds issue priority labeling, dependabot PR handling, and security-alert
assessment. The scope is deliberately narrow — no unattended execution, no new
labels, and no work outside the three areas below.

## The one hard rule

Discovery is read-only. Every write happens only after the maintainer approves a
plan row. See [Batch-plan protocol](#batch-plan-protocol).

Every comment posted to the issue tracker during maintenance **must** start with
this disclaimer:

```
> *This was generated by AI during maintenance.*
```

## Shared state machine

Four **category** roles (exactly one per issue):

- `bug`: something is broken
- `enhancement`: new feature or improvement
- `chore`: maintenance, refactoring, or tech debt
- `documentation`: improvements or additions to documentation

One optional **marker**, orthogonal to category and state and applied at most
once:

- `upstream`: depends on an external project (microsandbox, opencode, ...)

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

Every triaged issue carries exactly one category role and one state role; it may
additionally carry the `upstream` marker when the work depends on an external
project. If state roles conflict, flag it and ask the maintainer before doing
anything else.

`priority:*` labels are orthogonal and set per [PRIORITIES.md](PRIORITIES.md);
they are not part of the state machine. The dependabot ecosystem labels
(`dependencies`, `github_actions`, `go`) are out of scope: dependabot applies
them to PRs, which `maintain` does not triage.

These are canonical role names; the actual label strings are defined by the
tracker mapping (see `setup-matt-pocock-skills/triage-labels.md`). If the mapping
is missing, tell the user to run `/setup-matt-pocock-skills`.

State transitions and the full per-issue flow live in
[ISSUE-TRIAGE.md](ISSUE-TRIAGE.md).

## Invocation

The maintainer invokes `/maintain` and describes what they want in natural
language. Dispatch to the matching area and act through a batch plan:

- "Show me anything that needs my attention" → full survey
- "Handle dependabot" → [DEPENDABOT.md](DEPENDABOT.md)
- "Anything security?" → [SECURITY.md](SECURITY.md)
- "What needs triage?" / "Label #97 priority:high" → [ISSUE-TRIAGE.md](ISSUE-TRIAGE.md)
- "Merge #120" / "Close #42 wontfix" → direct action, still confirmed in a plan

The repo does **not** treat external PRs as a request surface (see the
issue-tracker config), so non-dependabot PRs are not a maintenance target. To
triage a named PR anyway, ask the maintainer first.

## Survey

Query the issue tracker and present one table spanning the areas, oldest first,
each row tagged by area. This is read-only.

- **Dependabot** — open dependabot PRs with semver level and check status.
- **Security** — open vulnerability alerts, plus any disabled-feature gaps.
- **Issues** — untriaged, `needs-triage`, and `needs-info` with reporter
  activity since the last notes, each with a proposed category/state/priority.

Show counts and a one-line summary per item. Include the maintainer in the
decision, but do not write yet.

## Batch-plan protocol

1. **Survey** read-only. Never write during discovery.
2. **Present one numbered plan.** Each row names the target, the action, and the
   rationale. Nothing is silent: items that cannot be actioned appear as
   explicit rows:
   - `skip:` — read-only; the item is reported for awareness, no write.
   - `flag:` — needs a human decision or human-only action. Executing an
     approved `flag:` row posts an explanatory comment naming the blocker (or,
     where the blocker is a skill limitation, reports it to the maintainer) and
     makes no state change.
3. **Wait.** The maintainer approves all, strikes rows, or edits. Do not start
   before an explicit yes.
4. **Execute approved rows only.** Immediately before each write, re-validate
   mutable state (checks, mergeability, current labels). If state changed since
   the plan was drawn, skip that row and report it.
5. Each posted comment carries the AI-disclaimer.
