# CI pipeline

## Job gating

`.github/workflows/ci.yml` always runs `lint` (`make lint`, `make compile-all`, `make validate-fmt`, `make docs-linkcheck`, `make docs-linkcheck-test`, `make ci-guards-check`, `make ci-guards-check-test`, `make actionlint`, `make cleanup-branches-test`), `test` (`make coverage-junit`), `race` (`make test-race`), `deadcode` (`make deadcode`), and `changelog` (`ci/check-changelog.sh`, which requires a `changelog.d/` fragment when the changeset touches code) — five of the six required branch checks, so none of these is gated and each runs on every event.

`vulncheck` (`make vulncheck`) is **not** required: it `needs: [changes]` and runs on a PR, main push, tag, or dispatch only when the `changes` gate reports `code=true`, and it is excluded from a merge group.

The `integration` job (`make test-integration`, the `integration`-tagged docker-build suite, ~10 minutes uncached) is **required** and runs:

1. on a `pull_request` when `needs.changes.outputs.code == 'true'` — every code-affecting PR, so the suite exercises PR code before merge. A PR touching only docs, the operator brain, the Homebrew formula, issue templates, the dev VM (`.agents-sandbox/`), or `.gitignore` sets `code=false`, skips the job, and reports Success.
2. on `startsWith(github.ref, 'refs/tags/')` — every release tag. `release` declares `needs: [lint, test, integration, integration-podman]`, so the integration jobs stay in this workflow; a second workflow would drop that gate.
3. on `github.event_name == 'workflow_dispatch'` — a manual run.

A **push** to `main` that sets `code=true` runs the same build as the separate `integration-cache-writer` job (`name: integration (docker build, cache writer)`) instead, because only that writer needs `packages: write` to export the cache (see the cache paragraph below). The writer's condition is `github.event_name == 'push'`, so a `workflow_dispatch` on `main` stays a reader — a manual run cannot overwrite `main`'s cache. The required `integration (docker build)` context reports Success-on-skip on a main push.

Neither the reader nor the writer runs on a `merge_group`: a skipped required check reports Success, so the queue satisfies the required `integration` check without paying the build (see [Merge queue](#merge-queue)).

The suite resolves each agent's latest release to bake into the image it builds (`internal/agent/latest.go`). Because shared runner IPs exhaust GitHub's anonymous 60-requests/hour limit, both `integration` and `integration-podman` export `GH_TOKEN: ${{ github.token }}` into the test process; the launcher authenticates the GitHub API queries with it, so the suite is subject to the authenticated limit instead of failing with `unexpected status 403`. The token is used only host-side, on `api.github.com`, and the non-GitHub release endpoints it also fetches (npm, `pi.dev`, the opencode2 update API) are never sent it.

The job is **cached** through the GHCR BuildKit cache backend (`type=registry,ref=ghcr.io/inoio/agents-sandbox:buildcache`), chosen because it has no Actions cache-budget cap (see the rationale below). `AGENTS_SANDBOX_IMAGE_CACHE_TO` (`…,mode=max`) is set **only** in the `integration-cache-writer` job, which runs only on a code-affecting push to `main`, so `main` is the single writer of the `buildcache` tags. `AGENTS_SANDBOX_IMAGE_CACHE_FROM` (`…:buildcache`) is set on every read-only `integration` run **except** a release tag: a tag is a validation run that builds from scratch, so a green release proves the build works uncached, and the writer's `_FROM` is empty so a main push also builds from scratch before exporting. Every reader run — a PR, a dispatch — restores from `main`'s export. A same-repo reader authenticates with the job's `docker login ghcr.io` (`packages: read`); a fork PR has a read-only token with no `packages` scope, so it skips both the login and the import and builds uncached rather than failing on an anonymous `403`. The reader never exports, so a PR or a compromised test dependency cannot push to the shared package — only the writer, whose `packages: write` is confined to the `integration-cache-writer` job, can. Each variable holds exactly one cache spec (the launcher's `image-cache-from`/`image-cache-to` keys are single strings for this reason); the suite keys the spec to a per-build value before handing it to BuildKit, and on an engine that advertises only the classic builder the specs are ignored and the cache is a no-op.

The suite keys each build's cache to its image tag (`imageCacheEnv` → `keyCacheSpec`, `internal/sandbox/image`): the `gha` backend keys on the `scope` attribute, the registry backend on the `ref`'s tag. Either location keeps only the newest chain written to it — gha's `SaveMutable` keeps the newest under a scope, and a registry tag moves to the last push — so with one shared location every build in a run wrote the same place, only the last build's chain survived, and the rest of the run's layers were unreachable, so a restore covered a fraction of the suite. A per-build key gives each build its own location to restore from and export to; layer blobs stay keyed by digest alone, so the extra locations cost no blob storage. Measured on restore-only runs: ~519 s for the integration package with the shared `gha` scope, ~351 s with per-build scopes; a GHCR restore measured ~394 s.

The suite's top-level cases run serially — only one top-level test runs at a time — but several of them parallelize their subtests internally: the `EveryAgent` group (its 14 harness×base pairs) and the Dockerfile render/build case groups (`TestRenderDockerfileBuilds`, `TestRenderDockerfileOwnsToolTreeOnPreProvidedDevBase`, `TestRenderDockerfileNodeAgentNodeRuns`). Do **not** parallelize the top-level cases: they share the daemon's single layer cache, and running them concurrently rebuilds the large shared stages (`agents-sandbox-node`, `-docker`, the hermes agent) and breaks the two tool-layer cache assertions. Measured (dispatch): ~519 s serial, ~465 s with naive top-level parallelism (fails `tool-layers-stay-cached` and `agent-version-rebuilds-install`), ~608 s with the shared layers primed serially first. The lever is a working cache, not a scheduler.

The backend moved off `type=gha` because that backend is bounded by the repository's Actions cache budget (read it with `gh api repos/<owner>/<repo>/actions/cache/usage`; the default is 10 GB): a `mode=max` export of this multi-stage render (`COPY --from=agents-sandbox-agent …`) is ~10 GB — essentially the whole budget — so each main push re-seeded and evicted the previous cache, and the oldest surviving `index-runner-image-…` entries dropped away between pushes, letting a PR silently build cold. GHCR has no comparable cap, but also no documented auto-GC: superseded cache manifests accumulate as untagged package versions until pruned. `mode=min` is not an option: only `mode=max` exports the intermediate layers the multi-stage cache chain needs, so `min` would cost hits without guaranteeing it fits. The integration job prints each build's cached-step ratio (to `AGENTS_SANDBOX_CACHE_REPORT`) so a regression to "imported but nothing matched" is visible in the log.

`integration-podman` runs the same suite against a rootless podman endpoint (the step starts `podman system service` and points `DOCKER_HOST` at its socket). It stays **opt-in** — the `run-integration-podman` label, plus tags, dispatch, and the main-push `changes` gate, but not a code-affecting PR by default — and is **not** required: podman serves the Docker API but advertises only the classic builder, so it neither exercises the BuildKit path nor benefits from the cache, and running it on every PR would add ~10 minutes for no BuildKit coverage. It holds podman to the claim that it is a tested Docker-compatible engine, so a podman-only failure has its own job and label and never blocks a PR.

`release` gates on `lint`, `test`, `integration`, and `integration-podman`: both the reference engine and the alternative engine must pass their build suite before a release publishes, and the tag's `integration` restores no cache, so that gate is a genuine from-scratch build. `race` and `vulncheck` run on a tag but do not block publishing, so a new reachable vulnerability cannot wedge a release.

### Merge queue

`main` merges only through a GitHub **merge queue** (the `protect main` ruleset's `merge_queue` rule: `MERGE` method, `ALLGREEN` grouping, up to 5 entries, a 60-minute check-response timeout). The queue builds the queued PRs on top of the current `main` on a throwaway `gh-readonly-queue/main/pr-<n>-<sha>` ref and runs the six required checks there, so a combination of two independently-green PRs that does not build is rejected before `main` moves.

The required set is `lint`/`test`/`race`/`deadcode`/`changelog`/`integration`. The first five run in parallel on every event — a queue cycle is about two minutes, bounded by `race` — and none depends on the network or on nondeterminism. `integration` is required too, but its condition excludes a `merge_group`, and GitHub reports a skipped required check as Success: the queue therefore satisfies the required `integration` check without running the ~10-minute (cached) build, and the post-merge push to `main` — where `code=true` — is what runs it and re-seeds the cache. So the queue does not pay the build and no image-build flake can eject a PR from it. `vulncheck`, `mutation`, `fuzz`, and `integration-podman` stay out.

`ci.yml` declares the `merge_group` trigger; without it the required checks never report on the queue ref and every entry is dropped on the check-response timeout. The always-run `changelog` job derives a merge group's base from `github.event.merge_group.base_sha`, since that payload carries no `before`; the `changes` job never runs on a merge group.

### Concurrency and the `changes` gate

The workflow sets `concurrency.group` to `ci-<ref>` for pull requests and a per-run id otherwise, with `cancel-in-progress: true` only for pull requests: a re-pushed PR cancels its superseded run, while a main push, tag, dispatch, or merge group is never cancelled or serialized.

The `changes` job reports whether the push changed anything that can affect the runner image or the tests — the complement of `mutation.yml`'s `paths-ignore` list (docs, `.operator-shared/`, `Formula/`, `.github/ISSUE_TEMPLATE/`, `.agents-sandbox/`, `**.md`, `.gitignore`). It diffs the event's base against `github.sha`: a push uses the payload's `before` tip, a pull request the base branch's merge base. A merge group never reaches the job — `if: github.event_name != 'merge_group'` skips it, leaving the step's `merge_group` base branch dead; the always-run `changelog` job handles that event with `github.event.merge_group.base_sha`. The skip is safe because no consumer reads the job on a merge group (the gated jobs all exclude `merge_group`): a skipped dependency skips them, the same Success-on-skip the queue already relies on, so the queue skips the full-history checkout and the diff too. The exempt list has four homes — this job's `grep -vqE`, `mutation.yml`'s and `codeql.yml`'s `paths-ignore`, and `check-changelog.sh`'s presence rule (which adds a `*_test.go` exemption) — and `ci/check-ci-guards.sh` (`make ci-guards-check`, in the always-run `lint` job) fails when one drifts from the others, since GitHub cannot compute a workflow's `paths-ignore` and each site must hardcode its copy. The set is deliberately coarse — every other path reports `code=true`, so `integration` runs — and two classes must stay in: a file that configures or invokes the guarded job (`ci.yml`, `Makefile`), whose edit reconfigures the build the job runs, and a non-Go input embedded into the module (`internal/sandbox/image/data/**`, `internal/notify/assets/**`, `go:embed`), which no `.go`-based rule would catch. Exempting a directory wholesale (`scripts/**`, `.github/**`) is unsafe for exactly that reason; `.agents-sandbox/**` (the dev VM) is the exception — nothing in the product or the CI test suite reads the repo's `.agents-sandbox/`, and `scripts/changed-targets.sh` already classifies it as no-target for the local loop. `vulncheck` `needs: [changes]` and, on a PR or main push, runs only when `code=true`; tags and dispatch always run it, and a merge group excludes it. `integration` `needs: [changes]` and requires `needs.changes.outputs.code == 'true'` on a pull request and on a `refs/heads/main` push; `integration-podman` requires it only on a main push. Tags, dispatch, and the podman PR opt-in label ignore the gate. `race` and `deadcode` are required, so they are not gated and always run: GitHub reports a job skipped by its `if` as Success, which would satisfy the required check without running it. CodeQL keeps its own equivalent `paths-ignore`.

### Invariants

- Every `github.event_name == '<event>'` a job condition references must be declared in the workflow's `on:` block. Breaking this is silent: the condition is merely never true. The same applies to an event consumed outside a job condition: the `protect main` ruleset requires checks that only report on `merge_group`, so `on:` must declare `merge_group` or nothing ever satisfies the queue. `ci/check-ci-guards.sh` (in the always-run `lint` job) enforces this invariant and the `types:` one below by scanning `ci.yml`; `actionlint` (`make actionlint`, also in `lint`) lints every workflow for general errors — invalid expressions, undefined contexts, shellcheck on `run:` — but checks neither of these two semantics.
- `on.pull_request.types` must list `labeled` **and** repeat the defaults (`opened`, `synchronize`, `reopened`): declaring `types:` replaces the default set rather than extending it. Enforced by `ci/check-ci-guards.sh`.
- Both `ci.yml` and `fuzz.yml` declare a workflow-level `permissions: contents: read`; the `publish` job raises its own (`contents: write`, `pull-requests: write`) to publish the Release and open the Homebrew bump PR. `mutation.yml` does the same for its sticky survivor comment. CodeQL's `actions/missing-workflow-permissions` query reports one alert **per job** with no effective limitation, so removing the workflow-level block reopens one alert per job.
- The `integration` job raises `packages: read` (to pull the private GHCR cache) and `integration-cache-writer` raises `packages: write` (to export it). The split is what keeps the saved `docker login` credential read-only on a PR or dispatch run, so neither can overwrite the shared cache. A job-level `permissions` block replaces the workflow-level one, not merges with it, so both repeat `contents: read`.
- GitHub only offers dispatch for workflows whose file exists on the default branch, so `workflow_dispatch` becomes usable when it reaches `main`.
- The label names have no single source of truth: each appears in its job condition, the job's comment, and CONTRIBUTING's Testing section. GitHub also needs a label to exist in the repository first; `run-integration-podman` is created there. `run-integration` (retired when the docker job became required and PR-default) and `run-mutation` (an earlier opt-in design) are now unused. Applying a label needs the repository's **triage** role or higher; a label a contributor sets in their own fork does nothing.
- The `protect main` ruleset requires `lint`, `test`, `race`, `deadcode`, `changelog`, and `integration`, and carries the `merge_queue` rule. A job skipped by its `if` reports Success, so a skipped required check *is* treated as passed — gating one would leave it green without running. A workflow skipped by path or branch filtering is the opposite: it leaves its checks Pending and blocks the PR. So `race`/`deadcode` are not gated at all, and `integration` — required but gated — relies on Success-on-skip to stay green on a docs-only PR and on the merge group while actually running on every code-affecting PR and main push; `vulncheck` (gated, not required) and `integration-podman` stay optional. The required check's context is the job's `name:`, so `integration`'s context is `integration (docker build)`, not `integration`; requiring it is a manual admin action on the ruleset (a workflow file cannot set it), so the `integration (docker build)` context must be added there or the job runs without being enforced. The ruleset requires the checks without `strict_required_status_checks_policy`; the merge queue, not strict, is the up-to-date guarantee.
- The gate is not a privilege boundary: `lint`/`test` already execute PR code on the same runner, so the podman label adds compute, not trust — the docker integration running on every code-affecting PR by default is at that same trust level. For fork PRs, `pull_request` withholds secrets and forces a read-only token; the integration job's only credential is that automatic token, used solely to authenticate its public release reads, so the trust level is unchanged. A first-time contributor's fork PR needs a maintainer's workflow approval before any job runs.
- Adding the `run-integration-podman` label re-runs the whole workflow, and the label persists, so every later `synchronize` push runs the podman job again.
- The `integration` build cache is asymmetric: `main` writes it but never reads it, a release tag neither reads nor writes it, and only a PR or a dispatch reads it. A validation run must not restore the cache, or a green `main` and release would not prove the image builds from scratch.

## CodeQL scanning

Code scanning runs from the committed advanced-setup workflow `.github/workflows/codeql.yml`, not GitHub's default setup. The repository's default setup must remain `not-configured`: the two cannot coexist, and an advanced analysis whose SARIF is uploaded while default setup is enabled is rejected. State is readable/set with `gh api repos/inoio/agents-sandbox/code-scanning/default-setup` (`-X PATCH … -f state=not-configured`).

The scanned languages mirror what default setup covered: `actions`, `go`, and `ruby`. Each is a matrix entry with its own `build-mode` — `none` for the interpreted languages, `autobuild` for Go. Go's autobuild runs with `CGO_ENABLED=1`, matching the Makefile, because the module binds the microsandbox FFI through cgo. The query suite is the default.

| Trigger | Notes |
|---|---|
| `push` to `main` | filtered by `paths-ignore` |
| `pull_request` | filtered by `paths-ignore` |
| `schedule`, weekly (`27 4 * * 1`) | the depth/coverage run |
| `workflow_dispatch` | a manual scan; ignores the paths filter |

The `paths-ignore` list is the complement of `ci.yml`'s `changes` gate and matches `mutation.yml`'s: `**.md`, `docs/**`, `.operator-shared/**`, `Formula/**`, `.github/ISSUE_TEMPLATE/**`, `.agents-sandbox/**`, `.gitignore`. A change to the workflow files or any code is not ignored, so `codeql.yml` edits scan themselves. Because `docs/**` is ignored wholesale, the Jekyll Gemfile is scanned only by the weekly run. CodeQL is **not** a required branch check, so a skipped or failing scan never blocks a merge.

Invariants: default setup stays disabled while this workflow is the scanner (re-enabling it silently breaks the upload); a language dropped from the matrix is a coverage loss invisible to CI, so all three stay until deliberately retired.

## Fuzz workflow

`.github/workflows/fuzz.yml` explores every fuzz target discovered in the module — the persisted state files (`state.FuzzParseState`), size and `--worktree` specs (`options.FuzzParseOptions`), configured mount-target validation (`mounts.FuzzResolveMountTarget`), the retired `updater.yaml` (`prepare.FuzzParseLegacyUpdaterState`), the project Dockerfile (`image.FuzzRenderDockerfile`), the `home:` manifest (`homeconfig.FuzzParseHomeSection`), `--older-than` durations (`viperconfig.FuzzParseHumanDuration`), and the naming package's round-trips (`naming.FuzzArtifactNameRoundTrip`, `naming.FuzzContentImageRefRoundTrip`, `naming.FuzzRunnerImageRefRoundTrip`) — on `ubuntu-latest`. These targets are pure Go: no KVM, no docker daemon, no network, so they run on a GitHub-hosted runner at all.

| Trigger | Budget passed to `make fuzz` | Why |
|---|---|---|
| `push` to `main` touching `internal/**`, `cmd/**`, or `test/**` | `60s` | attributable to the merge that broke it |
| `schedule`, nightly at `17 3 * * *` | `15m` | where depth comes from, accumulating into the corpus |
| `workflow_dispatch`, `fuzztime` input | the input (default `15m`) | an explicit long run before a release |

**Target discovery** is derived, not hardcoded. A `discover` job walks every `*_test.go` under `internal/`, `cmd/`, and `test/` that declares a `func Fuzz…`, emitting one entry per target — `{name, path, target}` — and the `fuzz` job builds its matrix from `fromJSON(needs.discover.outputs.targets)`. Adding a `func Fuzz...` joins the matrix with no workflow edit. The merge `paths` filter names the same three trees, so CI and the Makefile agree on what a target is by construction. `name` is the package path with `/` flattened to `-` plus the target, unique across the matrix, keying both the per-target corpus cache and the concurrency group.

One matrix job per target, because `go test -fuzz` accepts exactly one target per run; the workflow passes `FUZZPKG=<path>` and `FUZZTARGET=<name>` to `make fuzz`, which runs that target alone with `-fuzz='^Name$'`. `fail-fast: false` keeps one target's failure from hiding another's. `timeout-minutes: 45` bounds a single target.

Invariants:

- **Never a gate.** Fuzzing is not a PR check, not a step in `make check`/`make verify`, and not in `ci.yml`'s `release.needs`. What makes a finding durable is the committed corpus, not the run.
- **Discovery can never yield an empty matrix.** The `discover` job exits non-zero when it finds no target, mirroring `make fuzz FUZZPKG`, so GitHub's "matrix must contain at least one value" error can never be reached.
- **A cancelled run is a wasted run.** The concurrency group is `fuzz-<name>` with `cancel-in-progress: false`, so a new run waits for the in-flight one. GitHub still drops a superseded *pending* job.
- **The corpus accumulates in `$GOCACHE/fuzz`, cached per target.** The job restores `~/.cache/go-build/fuzz` from an `actions/cache` entry keyed `fuzz-corpus-<name>-<run id>-<run attempt>` with a `fuzz-corpus-<name>-` restore prefix: a unique key always saves (GitHub caches are immutable), the prefix restores the newest entry. It must not rely on `setup-go`'s cache — that entry is keyed on `go.sum` and is never re-saved on an exact hit, so discoveries would be thrown away.
- **A crasher leaves the runner as an artifact.** Go writes a failing input to the package's `testdata/fuzz/<Target>/` and prints it; the failing job uploads it for its matrix entry. CI does not commit the seed (needs a push token the workflow lacks) — a maintainer or agent commits it, and it then runs under `make test`.
- **`FUZZPKG`/`FUZZTARGET` fail loudly.** An unknown package, or a target matching nowhere, exits non-zero — a typo cannot read as a green run over zero targets.
- A schedule runs only from the default branch's copy of the workflow, and always against the default branch: the workflow is inert until it merges and never fuzzes a PR branch.

## Changelog fragments

Every behavior change adds a bullet under `CHANGELOG.md`'s `## [Unreleased]`, so any two PRs that share only that anchor conflict when the merge queue builds them together. `CHANGELOG.md merge=union` cannot fix this: GitHub's server-side merge and merge-queue build ignore `.gitattributes` merge drivers (evidence in `../../guides/github-merge-driver-support.md`). The fix is to stop editing one shared file.

### The fragment contract

A fragment is one file in `changelog.d/` at the repository root:

- **Name**: `<slug>.<type>.md`.
  - `<type>` is one of `added`, `changed`, `deprecated`, `docs`, `fixed` — exactly the `CHANGELOG.md` section.
  - `<slug>` is the **PR number** (unique by construction, which removes the conflict). An issue number is not: two PRs that close the same issue collide. A descriptive slug is not used either. The issue/PR reference (`(#432)`) stays in the bullet text, so the filename needs only uniqueness.
  - Several entries of the same type from one PR number them: `<slug>.<type>-<n>.md`, `<n>` from `1`. A single entry omits the ordinal.
- **Content**: exactly the text of one `CHANGELOG.md` bullet, without the leading `- `, continuation lines indented two spaces. One fragment becomes one bullet; a change spanning two sections uses two fragments.
- The directory may carry a short `README.md` (rendered in GitHub's directory view, read by agents). The check ignores the towncrier-standard set — `README.md`, `README.rst`, `README`, `.gitignore`, `.gitkeep`, `.keep`.

### Assembly contract

Fragments are assembled by the release process; there is no separate tool and no continuous writer to `main`. Between releases, `changelog.d/` is the live record.

- **Order**: sections in the fixed order `Added`, `Changed`, `Deprecated`, `Docs`, `Fixed`; within a section, fragments ordered by filename ascending, so assembly is deterministic.
- **Emission**: each fragment's first line is prefixed with `- ` and its remaining lines follow verbatim; the bullet is appended to its section's list.
- **Target**: at release the assembled content forms the new `## [X.Y.Z] - <date>` section, with any legacy `[Unreleased]` entries curated per the release process; the fragment files are deleted in the same change.
- The result keeps the Keep-a-Changelog shape and section headings. The vocabulary is closed: a new section is a deliberate change to this contract.

### Enforcement contract

Three rules, enforced by a dedicated `changelog` check that **always runs** and is a required status check. It must never be conditionally skipped (a skipped required check reports success; see the gating invariants). It decides the presence rule internally from the PR's diff rather than gating its own execution.

- **Shape** (every run): every file in `changelog.d/` matches `<slug>.<type>.md` (or `<slug>.<type>-<n>.md`) with a known type, except the ignored names.
- **Presence** (from the changeset, on every event): a changeset that touches production code must add at least one top-level, non-ignored fragment. "Production code" is the complement of the `changes` filter — `docs/`, `.operator-shared/`, `Formula/`, `.github/ISSUE_TEMPLATE/`, `.agents-sandbox/`, any `*.md`, and `.gitignore` are exempt — minus a further exemption for test files (`*_test.go`): a test-only changeset needs no fragment. An ignored name or a nested path under `changelog.d/` does not count. The job runs on the PR's diff and again on the queue/merge diff.
- **Slug** (`pull_request` events, where the number is known): a fragment the changeset adds must be present in the tree and its `<slug>` must equal the pull-request number, turning the add-before-the-PR-exists guess into a gate. `check-changelog.sh` takes `--pr NUMBER` for this; the CI job passes `github.event.pull_request.number`. A deleted fragment (the release PR removes every fragment when assembling `CHANGELOG.md`) is skipped, so the release PR is not compared against old numbers.

### Transition

Existing `## [Unreleased]` entries stay where they are and are consumed by the next release; they are frozen — from adoption on, no change edits `[Unreleased]` directly. After that first release the section is empty and `changelog.d/` is the only live record. Migrating the current entries into fragments is deliberately not done.

Non-goals: no change to the Keep-a-Changelog format or vocabulary beyond `changelog.d/`; no generation from commit messages/PR titles/labels; no bot or CI commit to `main`.
